# DevDeck deep dive — why it feels laggy, buggy and unsolid, and the plan

26 September 2026 · branch `claude/friendly-feynman-mwb9mp` · **revised 27 Sep after `feat/a-real-provider` merged into `main` — see §9, which supersedes parts of §4–§7**

Scope: the whole repository (≈67k lines Rust, ≈51k lines TS/TSX, 64 commits),
plus `d3velopm3nt/paperclip-v3` as the reference for an agent team. Findings
are marked **measured**, **verified** (read in the code, reproduced or
compiled), or **reported** (from an audit pass, not independently confirmed).
Two audit claims turned out to be wrong and are listed at the end so nobody
acts on them.

---

## 1. The short version

1. **The lag had two root causes, and both are mostly fixed on this branch.**
   Every log line and every 2-second stats sample re-rendered the entire window,
   hidden panels included. And almost every backend command ran on the UI
   thread, so git, disk scans and network calls froze the window while they ran.
   On a burst of 300 log lines, the window went from **2.9 fps and 11.6 s blocked**
   to **36 fps and 0.4 s blocked** (§2).
2. **One hotspot remains:** the Logs panel renders every row, up to 5,000,
   without virtualization. With the panel closed, a 4,000-line burst now holds
   60 fps. With it open, it drops to about 4.5 fps. This is the next fix.
3. **The "unsolid" feeling is scope, not one bug.** About 45% of the Rust lives
   in areas peripheral to *run my stack, watch it, and have agents work on it*:
   mail, learn, business setup, community store, calendar/life, stash. There
   are 15 rail views. The agent concept exists four times (bot, manager,
   business role, agent) with two turn loops and two UIs. Each area is
   individually reasonable. Together they create more surface than one person
   can keep correct.
4. **The agent layer is scaffolding around a workforce that isn't wired up
   yet.** Default agents run on the mock provider. The ROADMAP records that the
   Anthropic transport has never been run against the live API. Delegation to
   Claude Code exists (`aiw/cli_agent.rs`), but it runs in your working copy
   with no isolation, blocks the scheduler thread for the whole run, and hands
   Claude Code no skills, no MCP tools and no budget.
5. **The direction you already chose is right.** *The turn* in ROADMAP says
   DevDeck is the manager and Claude Code is the workforce. The plan below
   finishes that turn using the patterns that make paperclip robust, and cuts
   what does not serve it.

## 2. Lag — what was measured, fixed, and still open

### Measured (mock-IPC harness, real components and store, headless Chromium)

A chatty service was simulated at 1,000 lines/s through the production
listeners. "Blocked" is total main-thread long-task time. The baseline is
`97c80bc` (main); "fixed" is this branch.

| Scenario | Baseline | Fixed |
|---|---|---|
| 100 lines, Logs open | 2.5 s · 10.9 fps · 2.1 s blocked | 0.4 s · 51.7 fps · 0.05 s blocked |
| 300 lines, Logs open | 12.3 s · 2.9 fps · 11.6 s blocked | 0.8 s · 35.7 fps · 0.4 s blocked |
| 500 lines, Logs open | 31.2 s · 1.4 fps · 29.9 s blocked | (1,000 lines: 3.0 s · 17 fps) |
| 4,000 lines, Logs **closed** | 17.7 s · 23 fps · 13.4 s blocked | **4.3 s · 60 fps · 0 blocked** |
| 4,000 lines, Logs open | did not finish in 10 min | 35.6 s · 4.5 fps ← **open item** |

The baseline's cost grows faster than the line count, because each line copied
the whole log array and re-rendered everything. That is why a busy `npm run
dev` made the app feel like it was dying.

### Fixed on this branch (verified: `tsc -b` clean, lint unchanged, 611 Rust tests pass)

**Frontend**
- Logs and stats moved to their own store (`src/liveStore.ts`). About 60
  components subscribe to the *whole* main store, so those two feeds were
  re-rendering everything.
- Log lines land in one write per animation frame, and unchanged stats samples
  are dropped.
- The root `App` subscribes to the ~30 fields it reads instead of the whole store.
- Fixed a listener-leak race in nine components: cleanup ran before `listen()`
  resolved, so listeners were never removed. Under StrictMode, `Thread`
  streamed chat text twice.
- Debounced `data-changed`, which triggered a full vault scan plus git per
  project, and the Team board reload that fired on every agent event.

**Backend**
- 21 slow commands (git, vault scan, machine status, SQL runs, project
  detection/scan, file listings, update check, restart) now run off the UI
  thread. A plain sync `#[tauri::command]` runs on the main thread in Tauri 2.
- Log bus: `VecDeque` ring buffer, and one batched event per 50 ms instead of
  one IPC message per line.
- `vault_scan` walks the disk before taking the DB lock and writes the tree in
  one transaction instead of one commit per node.
- SQLite `synchronous=NORMAL` (safe under WAL) and `busy_timeout`.
- Startup: MCP sync, stash prune and OCR redaction moved off the path the
  window waits on.

### Still open (ranked)

| # | Issue | Evidence | Fix |
|---|---|---|---|
| L1 | Logs panel not virtualized: renders ≤5,000 rows, re-filters and scrolls on every flush | measured above; `LogViewer.tsx` | virtual list; filter incrementally |
| L2 | `Home` and `ServiceDetailPage` subscribe to the full log array to show a few lines | `Home.tsx:~123` | select a derived slice (last N for one service) |
| L3 | ~62 whole-store `useApp()` subscriptions remain | grep | per-field selectors; add a lint rule banning bare `useApp()` |
| L4 | ~265 commands still sync on the UI thread; each can stall behind a background thread holding the DB lock | 347 commands, heuristic scan | default new commands to async; convert DB-touching ones in batches (keep `pty_write` ordered) |
| L5 | Monitor spawns `netstat` and walks the full process table every 2 s, even when minimised (reported) | `monitor.rs:125,186` | `GetExtendedTcpTable`, targeted refresh, back off when hidden |
| L6 | One global `Mutex<Connection>`, 274 lock sites, `.unwrap()` on most — one panic while holding it poisons the DB for every later command | `db.rs`, grep | `parking_lot::Mutex` or a `db.conn()` helper that recovers; a read connection for the UI |
| L7 | A bot wake runs `wake_agent` **synchronously on the scheduler thread**; a 20-minute Claude Code run stops every reminder, routine and deadline | `schedule.rs:508,741` → `bots.rs:2407` | runs go to a worker pool (see §5) |
| L8 | Explorer, Stash, Mail and the Connections grid render full lists | reported | virtualize when touched |

## 3. Bugs found

**Fixed on this branch**
- **Garbled terminals:** PTY output decoded each 8 KB read on its own, so
  any character split across two reads became `�`. Box-drawing TUIs,
  including Claude Code's own UI, were hit constantly. Now carried over to
  the next read, with tests.
- **Event-triggered routines silently dropped:** `schedule::on_event` did
  `try_lock` and returned whenever the DB was busy, so "tests failed on
  master → wake the bot" simply didn't happen, and nothing said so. That
  breaks the project's own failure-honesty rule.
- **Log stream collision, again:** stash redaction logged under `-500_000`,
  which is the AI stream's id. That is the bug CLAUDE.md warns about,
  surviving as a raw literal the uniqueness test cannot see.
- **CI checked less than it appeared to:** typecheck ran `tsc --noEmit` on the
  references-only root config, which compiles nothing (the exact trap in
  CLAUDE.md), and the 611 Rust tests never ran. Both fixed.

**Open**
- Delegated runs share your working copy (`runtime.rs` → `cli_agent::run(...,
  &project.root, ...)`). Two agents, or you and an agent, edit the same files.
  Their changes interleave with yours and land in your next commit.
- A delegated session's completion never reaches the conversation, and
  `files_touched` is always empty, because reconciliation isn't built (ROADMAP
  *Known gaps*).
- `SessionCard` shows the last four transcript lines and there is no stop
  button. When work happens in another process, that transcript is the product.
- `CLAUDE.md` describes a 7-item rail. The code has 15 views, and ROADMAP
  reports the version and branch state as stale. The docs a new session reads
  first no longer match the code.

## 4. Why the architecture feels unsolid

1. **Too many products in one binary.** Each has its own backend module, IPC
   surface, store slice, sidebar, background thread and failure modes:

   | Area | Rust | TS | Serves the core loop? |
   |---|---|---|---|
   | Services · terminals · git · monitor · vault/spaces | ~9k | ~6k | **Yes, the product** |
   | AI: provider + assistant + runtime | 8.2k | — | Partly (see 3) |
   | AI Workspace UI (14 sub-pages, no rail button) | — | 5.4k | Duplicates Team |
   | Bots / managers / threads / botmind | 5.6k | ~3.7k | Yes, but four concepts for one |
   | Learn run (mail/business/life reading) | 5.3k | 2.3k | No |
   | Mail + Google auth | 5.2k | 1.6k | No (an MCP server can do this) |
   | Community store + index | 3.8k | 1.7k | No (Claude Code has plugins/skills) |
   | Business setup | 2.8k | 3.5k | No |
   | Stash + screenshots/OCR | 3.3k | 1.0k | Adjacent |
   | Calendar / focus / life / today | 1.0k | 2.5k | No |
   | Machine packages | 0.6k | 0.6k | **Yes — the paid wedge (manifests)** |
   | Connections (SQL) | 0.6k | 0.7k | Adjacent |

2. **One concept, many shapes.** *Bot* (`bots.rs`), *manager*
   (`managers.rs`, `.devdeck/team/*.md`), *business role*
   (`business_team.rs`) and *agent* (`AgentDef`) all describe "someone on the
   team who owns work". `Assistant::turn` and `AgentRuntime` are two turn loops.
   Three stores describe "what we know about you": `personal.rs` memory,
   `botmind.rs` and learn outputs. Routines, rhythms and schedules are one
   engine with three names.
3. **The AI works in the demo, not yet for real.** Default agents are `mock`.
   The Anthropic transport has never been run against the live API. The one
   real path (Claude Code delegation) is the least developed. Most of the 8k
   lines of provider/assistant/runtime exist to do in-house what Claude Code
   already does.
4. **Everything is shared and synchronous.** One DB mutex, UI-thread commands
   and background threads that call each other synchronously (scheduler → bot
   → agent run) mean one slow thing stalls unrelated things. That's the
   "sometimes it just hangs" feeling.
5. **State management has no enforced shape.** Two zustand stores (plus now
   the live store), bare `useApp()` everywhere, and module-level mutable
   globals in `App.tsx`. Nothing stops the next feature from re-creating §2.
6. **The safety net was thinner than it looked.** CI typechecked nothing and
   ran no tests, and there are no frontend tests. A green CI badge meant
   "it compiles on Windows".

None of this is sloppy code. The code is careful and heavily reasoned. The
problem is surface area outrunning one maintainer.

## 5. Target: a proactive agent team, with Claude Code as the workforce

### Principles

- **DevDeck decides, dispatches and verifies. Claude Code does the work.**
  No in-house coding loop.
- **Five nouns.** Agent, Skill, Goal, Item, Run, plus Approval as the gate.
  Everything else is a view of those.
- **Files for definitions, SQLite for state.** Agents and skills are markdown
  in the vault (git-friendly, editable, shareable). Items, runs, wakes and
  costs are rows, which makes checkout atomic and runs crash-recoverable.
- **Isolation by default.** Every run gets its own git worktree and branch.
  The review point is a diff or a PR, never your working copy.
- **Fail closed and fail loud.** Budgets hard-stop, approvals time out to
  *deny*, and a run that can't start is a failed run, never a silent no-op.

### The model

```
Agent  (.devdeck/team/<handle>.md)   role · goal · reports_to · skills[] · tools[] ·
                                      model · budget/month · rhythm (cron) · triggers[]
Skill  (.devdeck/skills/<name>/SKILL.md, plus ~/.claude/skills)   Claude Code's own format
Goal   (row)   what "done" means for a space; every item traces to one
Item   (row)   title · goal · assignee · status backlog→todo→doing→review→done|blocked ·
               parent · depth · checkout_run · branch/worktree
Run    (row)   agent · item · wake_reason · status queued→running→ok|failed|timeout|cancelled ·
               claude_session_id · cost · tokens · transcript file · diff summary
Approval (row) plan | merge | tool | spend — who asked, what, decided by, when
```

This collapses bot, manager, business role and agent into **Agent**, and
routine, rhythm and schedule into a **rhythm or trigger on an Agent**.

### How a run executes (replaces `drive_inner` and most of `provider.rs`)

1. **Wake:** from a timer, an assignment, an event trigger, or on demand.
   It becomes a `wake` row. If the agent is already running, the wake merges
   into that run instead of starting another (paperclip's *coalescing*).
2. **Checkout:** one conditional `UPDATE items SET checkout_run=? WHERE id=?
   AND checkout_run IS NULL AND status IN (...)`. If it loses, the result says
   who holds the item, and the run never retries. A stale lock from a dead run
   can be taken over.
3. **Worktree:** `git worktree add .devdeck-worktrees/<item> -b agent/<handle>/<item>`,
   in a folder outside the repo's tracked tree.
4. **Spawn** `claude -p` on a worker pool, never on the scheduler thread:
   - `--output-format stream-json --verbose`
   - `--append-system-prompt-file` with the agent's instructions and the
     assembled context. This replaces writing into `CLAUDE.md`, which fits the
     store split.
   - `--add-dir` for the skills folder (or `--plugin-dir` for a packaged team)
   - `--mcp-config` pointing to **DevDeck's own MCP server**, which exposes
     `item.comment/status/create/assign`, `approval.request`,
     `service.logs/status/restart` and `git.status`. Agents report back
     through tools, not stdout parsing. Every call carries the run id.
   - `--max-budget-usd` from the agent's remaining budget
   - `--permission-mode acceptEdits` plus `--permission-prompts none` when
     unattended (verified: both flags exist in the installed CLI)
   - `--resume <session>` when continuing the same agent and item
5. **Watch:** the stream feeds the run transcript file and the Logs panel. A
   real **Run view** has a full transcript, the diff so far, cost, and a
   stop button.
6. **Reconcile:** a git diff against the base gives `files_touched`, and the
   item moves to `review`. Depending on the agent's settings, it opens a PR or
   waits for an in-app diff approval. Nothing reaches your branch without a
   human merge.
7. **Reap:** at startup, runs left `running` by a crash become `failed`, with
   the reason written down.

Concurrency: at most one run per agent, a global cap (e.g. 3), and a
per-repo cap of one writer unless worktrees are on.

### What makes it proactive

A manager agent (plan-only: DevDeck MCP tools, no file edits) wakes on its
rhythm. It reads a compact **heartbeat context**: goals, open items, what
changed since last time, and triggers that fired. Then it creates and assigns
items. Built-in triggers use signals DevDeck already has and no CLI agent does:

- A service crashed or its health check failed → *investigate* item with the
  last 200 log lines attached
- A branch fell behind or has conflicts → *rebase/resolve* item
- Tests or CI failed on main → *fix* item for the owning agent
- A work item was stale for N days, or blocked → manager asks you, once (no
  "still blocked" spam)
- A dependency or package update is available (Machine) → *upgrade* item
- **Morning brief:** what moved overnight, what needs you, and spend to date

Every item carries `goal_id` and a `depth` limit, so delegation can't recurse
without bound.

### Governance

- **Plan approval:** for items above a size threshold, the agent's first run
  produces a plan (`--permission-mode plan`) and waits for you.
- **Budgets:** per agent and per month. Soft warning at 80%. Hard stop at 100%:
  the agent pauses and the reason is visible. Checked both when a wake is
  queued and when a run starts.
- **Permission matrix** (keep yours): it now gates which DevDeck MCP tools and
  which Claude Code tools (`--allowedTools`) an agent gets. The orchestrator
  appears in it like any other agent.
- **Audit:** every mutation records the run id.

### The UI, rebuilt around that loop — 5 rail items

1. **Today** — needs you: approvals, questions, reviews, failures; plus the brief
2. **Team** — board (items by status), agents (org chart and config), goals
3. **Runs** — live and past runs; the full transcript, diff and cost view
4. **Projects** — services, terminals, git, logs (today's core, unchanged)
5. **Settings** — including Machine (manifests)

### Borrow from paperclip / avoid

Borrow: atomic checkout tied to a run · the run ledger with coalescing and
reaping · callbacks through a tool API · skills and instructions as files
injected per run · budget hard-stops · resumable session per (agent, item) ·
goal lineage on every item.

Avoid: multi-tenant company scoping, auth and JWTs (single user, local) · a
4k-line heartbeat monolith · `--dangerously-skip-permissions` (your fail-closed
gate is stronger) · trust scores that loosen approvals · agent memory inside
repos (your vault/personal split is better).

## 7. The plan

Each phase ships on its own, keeps the app usable, and ends with the checks
green (tsc -b, lint, fmt, clippy, cargo test in CI).

**Phase 0 — done (this branch).** The lag fixes in §2 and bug fixes in §3,
with measurements.

**Phase 1 — Stabilise (small, low risk).**
- L1/L2: virtualize the Logs panel; stop `Home`/`ServiceDetailPage` reading the
  whole log.
  *Exit:* 4,000-line burst with Logs open at ≥50 fps in the harness.
- L7: move bot wakes and agent runs off the scheduler thread (interim: a thread
  per run plus a global cap). *Exit:* reminders fire on time during a long run.
- L6: DB access helper that doesn't poison, and replace `.lock().unwrap()`.
- L3: lint rule banning bare `useApp()`; convert the hot components.
- L4: convert DB-touching sync commands in batches.
- Keep the harness perf check as a script in `harness/`; wire it into CI later.
- Refresh `CLAUDE.md` and ROADMAP so they describe what exists.

**Phase 2 — Cut (needs your decisions in §8).** In order of least coupling:
orphans → AI Workspace UI → community → business → learn → botmind merge.
Mail and calendar freeze first; cut once the MCP replacements prove themselves.
One PR per area.

**Phase 3 — The run engine.** Schema for items, runs, wakes and approvals, with
atomic checkout and reaping. Worktree runner on a worker pool. DevDeck MCP
server (item/approval/service/git tools). The Run view (full transcript,
diff, cost, stop). Budgets.
*Exit:* assign an item to an agent → it runs in a worktree → you review the
diff → merge; plus a crash mid-run gets reaped.

**Phase 4 — The team.** Agent and skill files (one format; migrate bots,
managers and roles into it). Manager agents with plan-only permissions and a
heartbeat context. Goal lineage and depth limits. Plan approval. The Today
inbox.

**Phase 5 — Proactive.** Triggers from services, git, CI and packages. The
morning brief. Templates: "solo dev", "small agency", each a manager plus
specialists plus skills. This is also where team-shareable manifests connect
to the paid product.

## Appendix A — how the numbers were produced

`harness/` renders the real `App` against a mocked Tauri boundary. This
branch gave the mock a real in-page event bus (`window.__emit`) and exposed
the store (`window.__app`). The measurement script pushes N×50 log lines at
50 ms intervals plus stats samples, using `svc:log` (per-line, baseline) or
`svc:logs` (batched, fixed), matching what each backend emits. It records
`longtask` time and `requestAnimationFrame` count. Chromium, headless, 1440×900,
this container. Absolute numbers will differ on your machine and in WebView2;
the ratios are what matter.

## Appendix B — audit claims checked and rejected

- *"`--permission-prompts none` is not a real Claude Code flag."* Wrong: it
  exists (`claude --help`) and does what `cli_agent.rs` expects.
- *"`stash_items.file_path` has no index, so screenshot import does full scans."*
  Wrong: `stash_file` is a unique index on it (`db.rs:825`).

### What main now has that §4–§5 said was missing

| §4/§5 claim | Now on main |
|---|---|
| "Default agents are mock; the Anthropic transport never ran live" | The mock is no longer offered anywhere a person chooses a provider; an agent file naming a mock, a missing provider or one without credentials is refused with the reason. `ProviderSetup` tests credentials before it closes. A real manager→worker run built a goal tracker to 7 passing tests (`design/a-real-provider/TEST-REPORT.md`). |
| "Delegated runs share your working copy" | `workers.rs`: every `writes: branch` run gets its own **git worktree** in the personal store and its own branch; an interrupted run commits what it had and releases the branch (`close_orphans` at startup). |

enforced; `RunSlots` caps the clock at four in flight), a resumable session
per (worker, item), and a callback tool API beyond permission prompts.

  switch (an API provider talks in rooms, `claude-code` is a pair of hands).
  This is §5's *Agent*; the report's name for it changes to match.
- **One room per feature** (`design/one-room/BUILD.md`). The feature thread is
  where a manager hands over, a worker reports and you answer. Matches §5.
- **The AI Workspace stops being a place**: roster → Workers, provider config
  → Settings, Chat/Features/Git/ContextInspector deleted. That is §6's first
  cut, already agreed.
- **Today absorbs Dashboard and Inbox.**
- **Rail in four groups** — the work (Today · Items · Rooms), this space's
  folders, what is yours across spaces (Mail · Calendar · Team · Workers), and
  Tools folded away. This replaces §5's five-item rail. Mail and Calendar stay
  in the rail as "yours": consistent with **frozen, kept**.
- **GitHub issues as the roadmap** was "discussed, not decided" there; it is
  decided now (issues first, `devdeck-bot` identity, design in the repo,
  *Product studio* as the first template).

### Revised plan

## 10. The same check, in WebView2 (27 September)

§2's numbers came from headless Chromium against a mocked Tauri boundary, and
Appendix A said so plainly: *"absolute numbers will differ … in WebView2."*
They are measured there now. `harness/wv2-perf.mjs` drives the real app over
the WebView2 debugging protocol — a real service (`harness/chatty.js`) prints
1,000 lines a second, the real backend batches them, the real listeners take
them, and the Logs panel is opened by pressing the tab rather than by setting
the store. Nothing is written to the database behind the app's back.

**Frames per second is the wrong instrument here, and would have produced a
false pass.** This window holds ~32 fps whether a service is running or not, so
the first run reported 32 fps under load and 32 fps idle and read as a triumph.
What shows the cost is the browser's own cumulative main-thread task time,
sampled either side of the burst, with an idle run as the control.

| case | lines | main thread busy | script | layout + style | rows in DOM | fps |
|---|---|---|---|---|---|---|
| idle (control) | 1 | **0.7 %** | 0.004 s | 0 s | 35 | 32.4 |
| chatty, Logs **open** | 3,302 | **20.3 %** | 0.504 s | 0.094 s | 35 | 32.4 |
| chatty, Logs **closed** | 3,253 | **4.2 %** | 0.056 s | 0 s | 0 | 32.6 |
| chatty, Logs open, 20 s | 16,102 | **21.1 %** | 2.519 s | 0.479 s | 35 | — |

Three things worth keeping:

- **The cost no longer grows with the buffer.** 3,302 lines cost 20.3 % of the
  main thread; 16,102 lines cost 21.1 %. Flat. That is the fix, stated as a
  measurement: the baseline's cost grew *faster* than the line count, because
  every line copied the whole log array and re-rendered the shell.
- **L1 has landed and it shows.** 35 rows in the DOM at 16,000 lines, and the
  panel unmounts to 0 rows when collapsed. §2's table still lists L1 as open —
  `8997b40` closed it.
- **The panel is still where the money goes**: 20.3 % open against 4.2 %
  closed. A chatty service with Logs collapsed is now nearly free, which is
  what §2 meant by "the cost of the panel itself is the difference between the
  two".

Environment: WebView2 Edg/154.0.4258.37, 1440×900 (the harness's viewport), a
debug build, this machine.

**One caveat, so the table is not read as more than it is.** No before/after
ratio was taken *in* WebView2. The baseline lives on a commit whose frontend no
longer exists on this branch, and reproducing it would mean building pre-fix
code to race against post-fix code. The ratios in §2 remain the harness's;
these are absolutes for the branch as it stands. What they establish is that
the fix holds outside the harness — not by how much.
